# wardex limitation markers and loss reasons

Generated by `python -m wardex_sdk explain --all`. A limitation marker is a value of a span's `wardex.limitations` attribute: the span shipped, and this is what it is missing. A loss reason is a key of `wardex.diagnostics().losses`: something wardex did not record, counted.

## Limitation markers

### `parent_unresolved`

- **What happened:** wardex expected this span to have a parent, but no live span, framework id or trace header named one, so the span starts its own trace.
- **What it means for the data:** The span itself is real; its place in the tree is missing, so it can show up as a separate trace instead of under the run that caused it.
- **What to do:** Call init() before the framework starts its run, open the work inside a wardex span (wardex.span(), @wardex.agent), and pass trace headers across process boundaries (wardex.get_trace_headers(), wardex.continue_trace()).

### `unit_inferred_sole`

- **What happened:** Nothing live said which run this call belongs to, and exactly one run was live, so wardex attached the call to that run.
- **What it means for the data:** The parent is a deduction, recorded with wardex.parent_confidence 0.5: right whenever only that run could have made the call.
- **What to do:** Usually nothing. To make the edge certain, make the call inside the framework's own run, or inside a wardex span.

### `correlation_conflict`

- **What happened:** Two sources disagreed about this span's parent: a framework id pointed into one trace while the live context pointed elsewhere, or the context still named a run that had already ended.
- **What it means for the data:** wardex kept the live context's answer and marked the disagreement, so the edge may be wrong.
- **What to do:** Look for work that outlives its run (a task started inside a run and still running after it ended). If there is none, report it with init(debug=True) output.

### `alias_forgotten`

- **What happened:** The framework id this span's parent was looked up by had been dropped from a bounded table (max_entries_per_unit), so the parent came from a less specific source.
- **What it means for the data:** The span may hang off its run instead of the exact step that caused it.
- **What to do:** Raise LimitsConfig(max_entries_per_unit=...) for runs with very many steps.

### `context_propagation_degraded`

- **What happened:** This release never attaches this marker; it is reserved for a later one.
- **What it means for the data:** It would mean the span's context reached it only in part (a thread pool that copied the context at submit time), so its parent edge may be incomplete.
- **What to do:** Nothing to configure.

### `context_propagation_unavailable`

- **What happened:** This release never attaches this marker; it is reserved for a later one.
- **What it means for the data:** It would mean the runtime cannot carry context to this span at all, so every span below it starts its own trace.
- **What to do:** Nothing to configure.

### `unit_evicted`

- **What happened:** A run or session was still open when wardex's table of them was full (max_units, or max_sessions for Claude Agent SDK sessions), so wardex closed it early to make room. On a new root it means the run continues there after its first part was closed that way.
- **What it means for the data:** The span ends at the eviction instant, not when the run ended, and the run's later work may sit under a second root.
- **What to do:** Raise LimitsConfig(max_units=...) or LimitsConfig(max_sessions=...), or end runs you no longer use.

### `unit_interrupted`

- **What happened:** The run was cut off by a shutdown (a signal, wardex.close() or interpreter exit) before it finished.
- **What it means for the data:** The span ends at the shutdown; the run's real outcome was never observed.
- **What to do:** Let runs finish, or await them, before the process exits.

### `child_span_unclosed`

- **What happened:** This span's own end never came: its parent was torn down or evicted while it was open, so wardex closed it then.
- **What it means for the data:** Its end time is the teardown's and its status was not observed.
- **What to do:** Nothing to configure here; the parent's own marker (unit_evicted, unit_interrupted) says why it ended early.

### `unit_table_full`

- **What happened:** A run had more open children than max_entries_per_unit, so wardex closed this one, the oldest, early to admit a new one.
- **What it means for the data:** Its end time is when it was pushed out, not when the work finished.
- **What to do:** Raise LimitsConfig(max_entries_per_unit=...).

### `session_entry_table_full`

- **What happened:** A Claude Agent SDK session had more open tool calls, sub-agents or model responses than max_session_entries, so wardex closed the oldest early.
- **What it means for the data:** The span ends when it was pushed out, with status UNSET. A call that completes later ships a second span with the same call id, also marked: leave marked UNSET spans out of latency totals so the call is not counted twice.
- **What to do:** Raise LimitsConfig(max_session_entries=...).

### `adapter_uninstalled`

- **What happened:** The span was still open when wardex uninstalled its adapter (wardex.close(), a second init(), or interpreter exit), so wardex closed it.
- **What it means for the data:** Its end time is the uninstall's, not the framework's.
- **What to do:** Call wardex.close() after the work it should cover has finished.

### `patch_superseded`

- **What happened:** Another library replaced a function wardex had patched, so calls went through that library's patch instead of wardex's.
- **What it means for the data:** What wardex's patch would have recorded after the replacement is missing.
- **What to do:** Call wardex.init() after the other library installs its patches, or report the conflict.

### `instrumentation_degraded`

- **What happened:** wardex's own instrumentation failed here: an adapter or a parser raised, a worker could not start, a session ended before the CLI's last telemetry, or a Claude Agent SDK session started without wardex's hooks.
- **What it means for the data:** Something that belongs on this span, or below it, is missing because of wardex, not because the work did not happen.
- **What to do:** Re-run with init(debug=True) for the traceback and report it. For the Claude Agent SDK, call wardex.init() before creating the client or importing query.

### `tracking_reset_at_fork`

- **What happened:** The connection this span used was opened before os.fork(), and the child process started tracking it from scratch.
- **What it means for the data:** Parsing may have started mid-stream, and timing counts from the fork, not from the connect.
- **What to do:** Open connections after forking when exact data matters.

### `no_wire_evidence`

- **What happened:** The span was built from the framework's own account (the prompt and answer of a codex exec run), not from bytes wardex saw on the network.
- **What it means for the data:** Payloads are what the framework reported; instructions it adds around the prompt are not included.
- **What to do:** Nothing to configure.

### `possible_duplicate_chat`

- **What happened:** This release never attaches this marker; it is reserved for a later one.
- **What it means for the data:** It would mean an adapter's chat span may also have been recorded by the network capture.
- **What to do:** Nothing to configure.

### `stream_buffer_exceeded`

- **What happened:** This release never attaches this marker; it is reserved for a later one.
- **What it means for the data:** It would mean an MCP stdio stream outgrew max_stream_buffer_bytes and its parser stopped mid-stream.
- **What to do:** Nothing to configure.

### `tool_call_id_unavailable_in_process`

- **What happened:** The framework ran this tool in-process and did not hand over the tool-call id (for OpenAI Agents: the call could not be matched to exactly one request).
- **What it means for the data:** The tool span cannot be joined by id to the model message that asked for it.
- **What to do:** Nothing to configure.

### `snapshot_type_unknown`

- **What happened:** capture_state_snapshot() was given a type that is not a SnapshotType, so the snapshot was recorded as UNSPECIFIED.
- **What it means for the data:** The snapshot is kept; its type is not.
- **What to do:** Pass a wardex.SnapshotType member.

### `tool_name_collision`

- **What happened:** Two MCP servers expose tools whose names become the same name the Claude CLI sees, so this span's name cannot say which server ran the call.
- **What it means for the data:** The call may be recorded twice, or this span may be its only record.
- **What to do:** Give the servers' tools distinct names.

### `link_ambiguous`

- **What happened:** LangGraph named this step's trigger in a form with more than one reading (a node name containing '+'), so wardex did not add the link.
- **What it means for the data:** The causal link to the nodes that triggered this step is missing.
- **What to do:** Use node names without '+'.

### `connect_timing_unavailable`

- **What happened:** wardex saw no timed TCP connect for this connection (none was observed, or an asynchronous connect could not be timed on its own), so tcp_connect_ms is unset.
- **What it means for the data:** The connect time is unknown, not zero.
- **What to do:** Nothing to configure.

### `ttft_unavailable_h2`

- **What happened:** The streamed response came over HTTP/2, where wardex sees data frames but not the stream's event boundaries, so time-to-first-token is absent.
- **What it means for the data:** Time-to-first-token is unknown, not zero.
- **What to do:** Nothing to configure.

### `ttft_ipc_approximation`

- **What happened:** Time-to-first-token was measured where the agent CLI's output reached this process, not on the network.
- **What it means for the data:** It includes the subprocess's and the pipe's latency.
- **What to do:** Nothing to configure.

### `transport_timing_unavailable_subprocess`

- **What happened:** The model call ran inside an agent CLI subprocess; wardex saw only its output stream, not the network.
- **What it means for the data:** The span has no connection or network timing.
- **What to do:** Nothing to configure.

### `peer_unresolved`

- **What happened:** wardex could not read the peer's host and port (a unix socket, or a TLS layer with no socket address), so server.address is the TLS server name or 'unknown' and server.port is 0.
- **What it means for the data:** The call was captured; only its address is a placeholder.
- **What to do:** Nothing to configure.

### `body_cap_exceeded`

- **What happened:** An HTTP body was longer than wardex keeps of one, so it kept the first max_body_bytes (max_opaque_body_bytes for a content type wardex does not parse, and for a JSON request outside any span until its reply showed a model call), or what the shared max_in_flight_body_bytes had room for, and let the rest pass unrecorded.
- **What it means for the data:** The payload is a prefix; anything parsed from the rest of it is missing.
- **What to do:** Raise LimitsConfig(max_body_bytes=...), LimitsConfig(max_opaque_body_bytes=...), or LimitsConfig(max_in_flight_body_bytes=...) when many bodies arrive at once.

### `grpc_message_truncated`

- **What happened:** The last gRPC message in the captured body was incomplete, usually because the body was cut at max_body_bytes.
- **What it means for the data:** That message's payload is not whole.
- **What to do:** Raise LimitsConfig(max_body_bytes=...).

### `ws_payload_truncated`

- **What happened:** The WebSocket content sample reached ws_sample_bytes.
- **What it means for the data:** The payload on this span is the start of the conversation, not all of it.
- **What to do:** Raise LimitsConfig(ws_sample_bytes=...).

### `connection_evicted`

- **What happened:** wardex's connection table reached max_connections, so tracking of this connection ended early.
- **What it means for the data:** The span ends at that moment; a WebSocket session goes on unwatched, with no length and no sizes.
- **What to do:** Raise LimitsConfig(max_connections=...).

### `h2_request_evicted`

- **What happened:** The HTTP/2 stream table reached max_streams and dropped this stream's request half before its response finished.
- **What it means for the data:** Method, path and request body are missing (shown as '? /'); status and response were observed.
- **What to do:** Raise LimitsConfig(max_streams=...).

### `parse_skipped_at_shutdown`

- **What happened:** The process was ending and its shutdown budget ran out before wardex parsed this response's model-call fields.
- **What it means for the data:** Transport, timing and status were measured; the gen_ai fields are absent.
- **What to do:** Give shutdown more time: wardex.close(timeout=...) or BatchingConfig(shutdown_timeout=...).

### `otlp_attribute_truncated`

- **What happened:** An attribute value was longer than max_otlp_attribute_bytes on export, so the backend shows its start only. When the span also carries wardex.payload_dropped.reason = max_otlp_request_bytes, its whole payload was removed so the span fits in one request.
- **What it means for the data:** What the backend shows is a prefix of what wardex captured, or no payload at all.
- **What to do:** Raise LimitsConfig(max_otlp_attribute_bytes=...), or LimitsConfig(max_otlp_request_bytes=...) for a dropped payload, if the backend accepts more.

### `extra_keys_dropped`

- **What happened:** A provider's usage object had more fields than max_extra_keys, so some wardex.usage.* fields were left out; wardex.usage_leaves.dropped_count says how many.
- **What it means for the data:** Some provider-specific usage counters are missing.
- **What to do:** Raise LimitsConfig(max_extra_keys=...).

### `parse_backlog_full`

- **What happened:** Too many responses were waiting to be parsed (max_parse_backlog, max_parse_backlog_bytes), so this one shipped without being parsed.
- **What it means for the data:** Transport, timing and status were measured; the gen_ai fields are absent, and the raw bodies may be withheld.
- **What to do:** Raise LimitsConfig(max_parse_backlog=...) or LimitsConfig(max_parse_backlog_bytes=...).

### `frame_parse_failed`

- **What happened:** wardex could not read this exchange's framing: gRPC or WebSocket frames, or an HTTP/1 response whose stream ended before its declared length.
- **What it means for the data:** The transport fields are partial: the body is what arrived, its size may be unset, and a 2xx status is UNSET. On a WebSocket, a frame over max_ws_frame_bytes also causes it.
- **What to do:** On HTTP, look at the server or network that ended the response early. On a WebSocket with large frames, raise LimitsConfig(max_ws_frame_bytes=...).

### `semantic_parse_failed`

- **What happened:** The body was read, but wardex could not understand it as a model call or as an MCP tool result it could vouch for.
- **What it means for the data:** The span has transport data and no gen_ai fields.
- **What to do:** If the provider should be supported, report it with init(debug=True) output.

### `payload_compressed`

- **What happened:** The payload was compressed (gRPC message compression, or WebSocket permessage-deflate) and wardex does not decompress it.
- **What it means for the data:** The body bytes on this span are not readable content.
- **What to do:** Nothing to configure.

### `tool_args_unparsed`

- **What happened:** A tool call's arguments were not valid JSON.
- **What it means for the data:** They are kept as one opaque string.
- **What to do:** Nothing to configure.

### `output_messages_unmapped_part`

- **What happened:** The model's response held a part wardex does not map, so gen_ai.output.messages leaves it out.
- **What it means for the data:** The response, as recorded, is incomplete.
- **What to do:** Upgrade wardex-sdk, and report it if it persists.

### `input_messages_unmapped_part`

- **What happened:** The prompt held a part wardex does not map, so gen_ai.input.messages leaves it out.
- **What it means for the data:** The prompt, as recorded, is incomplete.
- **What to do:** Upgrade wardex-sdk, and report it if it persists.

### `provider_inferred`

- **What happened:** gen_ai.provider.name was inferred from a host name that merely contains the provider's name (a proxy, a mock, an Azure deployment), or from the shape of the body or API, not read off the provider's own host.
- **What it means for the data:** The provider label may be wrong.
- **What to do:** Nothing to configure.

### `reassembled_from_stream`

- **What happened:** The response was streamed, and the body on this span is wardex's reassembly of the stream's events.
- **What it means for the data:** It is not one response the server sent as such.
- **What to do:** Nothing to configure.

### `stream_usage_unavailable`

- **What happened:** The streamed response carried no usage block.
- **What it means for the data:** Token counts are absent, not zero.
- **What to do:** If the provider can include usage in a stream, ask it to.

### `sse_unknown_provider`

- **What happened:** An event stream was reassembled but matched no provider format wardex knows.
- **What it means for the data:** No model-call fields were read from it.
- **What to do:** If the provider should be supported, report it.

### `sse_event_unparsed`

- **What happened:** An event in the model's stream was not valid JSON (cut short, or not JSON at all), so wardex skipped it.
- **What it means for the data:** Whatever that event carried may be missing from the span.
- **What to do:** If the span also carries body_cap_exceeded, raise LimitsConfig(max_body_bytes=...).

### `grpc_web_unsupported`

- **What happened:** The exchange used gRPC-Web, whose framing wardex does not parse.
- **What it means for the data:** It is recorded as plain HTTP/2.
- **What to do:** Nothing to configure.

### `grpc_status_unavailable`

- **What happened:** No grpc-status was seen (a trailers-only response, or trailers wardex did not observe).
- **What it means for the data:** The span's status comes from HTTP alone.
- **What to do:** Nothing to configure.

### `ws_no_close`

- **What happened:** The WebSocket span was emitted without a CLOSE frame: the socket closed, or wardex.close() stopped watching it.
- **What it means for the data:** There is no close code.
- **What to do:** Nothing to configure.

### `ws_llm_semantics_unread`

- **What happened:** This WebSocket carried model calls (the OpenAI Responses API over WebSocket), and wardex does not parse those events.
- **What it means for the data:** The span has transport counts and payload samples, but no model, tokens or messages.
- **What to do:** Use the framework's HTTP transport for full spans; for openai-agents that is use_responses_websocket=False, the default.

### `session_aborted`

- **What happened:** The agent session ended without a clean result: it raised, or ended with no result message.
- **What it means for the data:** The run did not complete normally.
- **What to do:** Look at the run's own error; there is nothing to configure in wardex.

### `otel_bridge_no_data`

- **What happened:** The OTel bridge configured the agent CLI's telemetry, confirmed the setting reached the subprocess, and still received nothing before the session ended.
- **What it means for the data:** The tree is what wardex records without the bridge.
- **What to do:** Check the CLI's version, and any policy that strips a subprocess's environment or blocks loopback connections.

### `otel_bridge_schema_unknown`

- **What happened:** Bridge telemetry arrived for this session but held nothing the bridge recognizes.
- **What it means for the data:** The tree is what wardex records without the bridge.
- **What to do:** Upgrade wardex-sdk; the CLI's telemetry format may have changed.

### `otel_bridge_join_tolerant`

- **What happened:** This chat span took its timing from a CLI request that matched it only within a one-second tolerance.
- **What it means for the data:** Read the timing as an estimate: it may be a neighbouring request's.
- **What to do:** Nothing to configure.

### `subprocess_model_calls_unobserved`

- **What happened:** The agent CLI (codex exec) reported one usage total per turn and no model calls, so no chat spans were recorded; the run's span carries the total.
- **What it means for the data:** Per-call model, usage and timing are missing.
- **What to do:** Pass AdaptersConfig(codex_exec=CodexExecConfig(otel_bridge=True)) to record each call from the CLI's own telemetry.

### `pii_filter_failed`

- **What happened:** PII masking failed on this span or snapshot, so wardex removed its content rather than ship it unmasked.
- **What it means for the data:** Only ids, kind and times remain, named [PII_FILTER_ERROR].
- **What to do:** This is a wardex bug; report it.

## Loss reasons

### `network_error`

- **What happened:** The batch never reached the receiver: the connection was refused, the name did not resolve, or connecting timed out.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Check that the receiver's address is reachable from this process.

### `send_error`

- **What happened:** The receiver refused the batch for good (a 4xx, or a 5xx not worth retrying), or the transport raised while sending it.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Check the project key and the receiver's status; a transport that raises is a bug.

### `ratelimit_backoff`

- **What happened:** The receiver asked wardex to back off (HTTP 429, or a wardex receiver's 503) and the batch was not sent.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Export less often (raise BatchingConfig(flush_interval=...)) or ask the receiver for a higher limit.

### `send_unconfirmed`

- **What happened:** Whether the batch arrived is unknown: no answer came back (a read timeout, a connection cut before the answer, a 502/504, or a budget that ran out mid-request).
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Give flush()/close() a larger timeout, or check the network path to the receiver.

### `request_too_large`

- **What happened:** Too large to send: a request over the receiver's size limit, or a single span over max_otlp_request_bytes even without its payload.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Raise LimitsConfig(max_otlp_request_bytes=...) if the receiver accepts more.

### `budget_exhausted`

- **What happened:** A batch split into several requests ran out of time before the rest were sent.
- **What it means for the data:** What it counted is gone. Counted per `request` by default.
- **What to do:** Give flush()/close() a larger timeout, or lower LimitsConfig(max_buffer_spans=...).

### `partial_success`

- **What happened:** The OTLP backend accepted the request but rejected some of its spans.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Read the backend's own logs for why those spans were rejected.

### `unmarshallable`

- **What happened:** The span held a value of the wrong type and could not be encoded.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Re-run with debug=True to see which span and value.

### `transport_unsupported`

- **What happened:** The configured transport cannot carry this kind of item (OTLP carries no state snapshots).
- **What it means for the data:** What it counted is gone. Counted per `snapshot` by default.
- **What to do:** Send to a wardex receiver to keep state snapshots.

### `queue_overflow`

- **What happened:** The buffer was full, so the oldest items were evicted before they were exported.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Raise LimitsConfig(max_buffer_spans=...) or LimitsConfig(max_buffer_bytes=...), or export more often (lower BatchingConfig(flush_interval=...)).

### `cache_overflow`

- **What happened:** The queue holding batches for a retry was full, so a held batch was dropped (counted in spans, or in requests for part of a split batch).
- **What it means for the data:** What it counted is gone. Counted per `request` by default.
- **What to do:** Restore the receiver, or check that its address is the right one; the retry queue's size has no setting.

### `before_send`

- **What happened:** before_send_envelope returned None: the host dropped the batch on purpose.
- **What it means for the data:** Nothing was lost: the count records a choice made on purpose. Counted per `span` by default.
- **What to do:** Nothing to do unless the filter drops more than intended.

### `before_send_error`

- **What happened:** before_send_envelope raised, so the batch was dropped unsent.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Fix the hook; re-run with debug=True for its traceback.

### `after_close`

- **What happened:** Captured after close(), when nothing would ever export it.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Call close() after the work it should cover, or init() again before more work.

### `shutdown_tail`

- **What happened:** Still buffered when close() or a shutdown signal ran out of time to send it.
- **What it means for the data:** What it counted is gone. Counted per `span` by default.
- **What to do:** Give close() a larger budget (BatchingConfig(shutdown_timeout=...)), or flush() before exit.

### `backpressure`

- **What happened:** The span shipped without its parsed gen_ai fields: the parse queue was full.
- **What it means for the data:** What it counted shipped, missing part of itself. Counted per `span` by default.
- **What to do:** Raise LimitsConfig(max_parse_backlog=...) or LimitsConfig(max_parse_backlog_bytes=...), or reduce the burst of model calls.

### `internal_sdk_error`

- **What happened:** wardex raised inside itself and swallowed it; what that step handled may be lost.
- **What it means for the data:** What it counted is gone. Counted per `failure` by default.
- **What to do:** Re-run with debug=True for the traceback, and report it.

### `diagnostic_unwritable`

- **What happened:** A wardex warning could not be written: stderr or a host log handler failed.
- **What it means for the data:** What it counted is gone. Counted per `failure` by default.
- **What to do:** Check stderr and any handler attached to the wardex_sdk logger.

### `ledger_overflow`

- **What happened:** More drop reports awaited confirmation than the ledger holds; the oldest was dropped.
- **What it means for the data:** What it counted is gone. Counted per `report` by default.
- **What to do:** Restore the receiver; repeated send_unconfirmed counts say why reports piled up.

### `mode_refused`

- **What happened:** capture_mode=AGENT declined an exchange outside any span that it keeps only inside a span: one it did not recognize as a model call, or a call to a model API it does not parse yet (Gemini, Bedrock, Cohere, Ollama).
- **What it means for the data:** What it counted is gone. Counted per `request` by default.
- **What to do:** Open a span around the work, or pass init(capture_mode=CaptureMode.ALL).

### `excluded_by_policy`

- **What happened:** Left out by design (a framework's own telemetry upload).
- **What it means for the data:** Nothing was lost: the count records a choice made on purpose. Counted per `request` by default.
- **What to do:** Nothing to do.

### `parser_disabled`

- **What happened:** A protocol parser stopped reading a connection or stream; what followed on it was not captured.
- **What it means for the data:** What it counted is gone. Counted per `connection` by default.
- **What to do:** Re-run with debug=True to see which connection and why.

### `response_unobserved`

- **What happened:** The request was seen but no response was (a timeout, a cancellation, a reset).
- **What it means for the data:** What it counted shipped, missing part of itself. Counted per `request` by default.
- **What to do:** Nothing to configure; the request half is what the network gave.

### `request_unobserved`

- **What happened:** A response was seen whose request was not (a connection opened before init()).
- **What it means for the data:** What it counted shipped, missing part of itself. Counted per `request` by default.
- **What to do:** Call init() before opening connections.

### `connection_evicted`

- **What happened:** The connection table was full, so an exchange in progress was evicted.
- **What it means for the data:** What it counted is gone. Counted per `request` by default.
- **What to do:** Raise LimitsConfig(max_connections=...).

### `in_flight_at_close`

- **What happened:** An exchange was still in progress when close() or a re-init uninstalled capture.
- **What it means for the data:** What it counted is gone. Counted per `request` by default.
- **What to do:** Close after in-flight requests finish.

### `unclassified_connection`

- **What happened:** The first bytes seen on a connection were a response, so it was never tracked.
- **What it means for the data:** What it counted is gone. Counted per `connection` by default.
- **What to do:** Call init() before opening connections.

### `table_full`

- **What happened:** A bounded table was full and evicted an entry; the unit says which table.
- **What it means for the data:** What it counted is gone. Counted per `entry` by default.
